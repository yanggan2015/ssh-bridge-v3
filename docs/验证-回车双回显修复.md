# 验证报告 · 修复“按一次 Enter 回显两次”

- 日期：2026-11-22
- 构建：`output/build/ssh_bridge3.exe`（修复后，无 warning）
- 环境：Windows 本机，150% DPI
- SSH：`ssh-link-demo1` 39.97.234.200:52222
- 串口回环：`loop1`（`loop:ai`，115200）
- 桥接：`http://127.0.0.1:18086`

## 一、现象

在 SSH 通道按一次 Enter：

```
ssh-demo-1:~$ echo DOUBLE_BEFORE
DOUBLE_BEFORE
ssh-demo-1:~$
ssh-demo-1:~$
```

命令只执行一次（`DOUBLE_BEFORE` 只输出一行），但回车后又多出一个空提示符。
串口回环上则表现为发送字节数比预期多 1。

## 二、根因

1. SSH 通道未显式配置 `line_ending`，配置层默认成 `crlf`。
2. `TerminalView::line_ending_bytes()` 对 `crlf` 返回 `"\r\n"`。
3. SSH PTY 是 Unix 行规程：CR 与 LF 都会各自作为一次换行提交。
   - `CR` 提交当前行；
   - 紧接着的 `LF` 又提交一个空行。
4. WM_CHAR 的 Enter、桥接 `term.input` 的自动回车都走同一个 `line_ending_bytes()`，因此两条路径都会双提交。

`WM_KEYDOWN` 不重复发送：`is_special_key(VK_RETURN)` 为 false，Enter 只由 WM_CHAR 处理；问题不是按键重复，而是**行尾两个字节**。

## 三、修复

`TerminalView::line_ending_bytes()` 按传输类型归一：

| 通道 | 配置 | 实际发送 |
| --- | --- | --- |
| SSH | `crlf`（默认） | 单个 `\r` |
| SSH | `cr` | 单个 `\r` |
| SSH | `lf` | 单个 `\n` |
| SSH | `none` | 不发送 |
| 串口 | `crlf` | `\r\n`（保持配置不变） |
| 串口 | `cr` / `lf` / `none` | 按配置 |

这样既修掉 SSH 的空提示符，又不改变串口板端对行结束符的既有约定。

## 四、真机验证

### 4.1 物理 Enter 路径

方式：`term.send` 只输入文本不回车，再向 `term.view` 投递真实 `WM_CHAR(13)`。

- 修复前：命令执行一次，但出现 **两个提示符**（`before.png`）
- 修复后：命令执行一次，只出现 **一个提示符**（`after-physical.png`）
- 命令：`echo PHYSICAL_ENTER`
- 输出：`PHYSICAL_ENTER`
- 终端 RX 从 0 增长到 94 B，无空行重复提交

### 4.2 桥接自动提交路径

`term.input set_text 'echo 中文_OK'`（内部 submit=true）：

```
ssh-demo-1:~$ echo 中文_OK
中文_OK
ssh-demo-1:~$
```

中文原样上行、输出正常，只有一个提示符。

### 4.3 退格 + Enter

`term.send 'echo EDIT_OKX'` → 真实 `WM_KEYDOWN(VK_BACK)` → 真实 `WM_CHAR(13)`：

- 命令被修正为 `echo EDIT_OK`；
- 输出 `EDIT_OK`；
- 只有一个提示符，无第二次提交。

### 4.4 串口回环

`loop1` 上 `term.input 'SERIAL_OK'`：

- 上行字节 11 B = `SERIAL_OK`（9 B）+ `CRLF`（2 B），与串口配置一致；
- 回显 `SERIAL_OK`；
- 没有改变串口行尾行为。

### 4.5 连发/重复 Enter

- 连发命令，每条命令一个提示符；
- 再按一次 Enter（空命令）只多一个空提示符，属正常 shell 行为，不再成对多出。
