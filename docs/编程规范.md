# 编程规范（v3）

适用范围：本仓全部 C/C++ 代码、脚本、文档改动。与 `docs/每步测试闸门.md` 配套执行；冲突时以闸门为准。

## 1. 提交粒度：一个提交 = 一个最小功能单元

- 一个提交只做一件事。新增一个通道字段、修一个回显 bug、加一个 API，各自一个提交；**禁止把"顺手改"混进功能提交**。
- 单次提交原则上 ≤ 5 个文件、≤ 300 行 diff。超过则拆；结构性重构（改名、拆文件、换接口）可例外，但必须在提交正文写明理由与影响面。
- 每个提交必须能**独立编译通过**、独立通过它所属步骤的闸门；不允许提交"半截代码等下一步接上"。
- 文档与实现分开提交：`docs:` 单独一笔，便于回滚代码而不丢文档。

## 2. 先测后提交

- 新增或修改功能，必须**先**在 `tests\CHECKLIST_stepN.md` 增加或更新对应条目，并补齐自动化检查（能脚本化的一律脚本化）。
- 跑过再提交：`tests\stepN_check.ps1` 退出码为 0，人工项在提交正文里附上截图路径或操作记录。
- 未通过就**不提交**。本地可以留 WIP，但不许进 `main`、不许写"下一步再修"。

## 3. 提交信息：必须说清"改了什么 / 为什么 / 怎么验"

固定格式：

```
<type>(stepN): <一句话结论，≤ 50 字>

改了什么：<模块 / 文件 / 行为>
为什么：<对应的验收编号 或 缺陷现象>
怎么验：<命令 + 关键输出，例如 tests\step1_check.ps1 → 8/8 PASS>
影响面：<会不会动到已有通道 / 配置 / 端口>
```

`type` 取值：

| type | 用于 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修缺陷 |
| `test` | 只加/改测试 |
| `refactor` | 不改外部行为的结构调整 |
| `docs` | 只改文档 |
| `chore` | 构建、脚本、依赖 |

反例（禁止）：`更新`、`修复bug`、`改了一些东西`、`提交`。

## 4. 编译清洁：error 必修，warning 尽量清零

- 编译开关固定 `-Wall -Wextra`（后续加 `-Wshadow`、`-Wconversion` 时按同样规则处理）。
- **error 必须为 0**，没有例外。
- **warning 逐条处理，能修就修**——不管是否影响功能：未使用变量/参数、有符号无符号比较、窄化转换、`printf` 格式串与参数不匹配、隐式 `double→int`、`switch` 缺分支。
- 只有在**第三方头文件或第三方库内部**产生的 warning 可以保留，且必须满足三条：① 提交正文列出 warning 原文与来源文件；② 只在该 `#include` 局部范围临时 `#pragma` 抑制，并注释原因；③ **绝不修改第三方源码**。
- 禁止全局关闭 warning（`-w`、整文件 `#pragma GCC diagnostic ignored`）；禁止为消 warning 引入无意义强转或 `(void)` 糊弄。
- 每次提交前编译输出必须贴进提交正文的关键行：`0 error, 0 warning`，或说明剩余 warning 的第三方来源。
- **交付物零第三方 DLL 依赖**：`ssh_bridge3.exe` 必须全静态链接（`-static`），验收时用 `objdump -p output\build\ssh_bridge3.exe | Select-String 'DLL Name'` 复核，只允许 `KERNEL32/USER32/GDI32/COMCTL32/SHELL32/msvcrt` 这类系统 DLL。出现 `lib*.dll` 即为不合格。

## 5. 代码整理（与 quality_gate 一致）

- `scripts\quality_gate.ps1` 必须 PASS：无 TAB、无行尾空白、单行 ≤ 200 字符、文件末尾有换行。
- 分层不变式：`core` 不依赖 `ui` / `services`；`services` 只依赖 `core`；`app` 是唯一装配层。
- 单文件业务代码 ≤ 800 行；单函数 ≤ 60 行；嵌套 ≤ 4 层。超了就拆，不许"先堆着"。
- 扩展只准加、不准改本体接口。发现必须改，先改设计文档再写代码。

## 6. 提交前 5 条自检

- [ ] 这次只做了一件事，diff ≤ 300 行（或已写明例外理由）
- [ ] 编译 `0 error`，warning 已处理或已注明第三方来源
- [ ] `tests\stepN_check.ps1` 全绿，清单条目已更新
- [ ] `quality_gate.ps1` PASS
- [ ] 提交信息写清了 改了什么 / 为什么 / 怎么验 / 影响面

## 7. 修复不许破坏相邻功能（硬性规则）

**任何功能修复，先评估影响面，再动代码；修完必须证明相邻功能仍绿。禁止“修一个、坏一个”的循环。**

### 7.1 动代码前必须写影响面矩阵

在 `tests/CHECKLIST_stepN.md` 或提交正文中先列出三圈影响：

| 圈层 | 必填内容 | 例子 |
|---|---|---|
| 直接 | 本次改的函数 / 文件 / 数据结构 | `SerialBridge::running()`、`AppCore::Entry` |
| 相邻 | 共用该数据、状态或生命周期的功能 | 串口启动/重连/断开、状态栏在线数、Web `/state` |
| 全局 | 启动、退出、配置读写、端口、UI 主流程 | 冷启动、托盘隐藏、配置保存、18081/18096 |

矩阵必须写明每项的**预期行为**与**验证手段**，不能只写“应该没事”。

### 7.2 修复必须成组回归

- 至少运行：① 被改模块的专项清单；② 矩阵中全部“相邻”项；③ 全局冒烟（编译、启动、配置读取、Web/Agent 健康、退出无残留）。
- 触及配置、窗口、生命周期、端口、线程退出语义时，**必须再加跑上一阶段的全量回归套件**，不能只跑本模块。
- 同一根因族要一次扫干净：例如串口线程退出未改状态，就同时检查 RX、writer、overlapped 失败、`stop()`、`running()`，不许只补一个分支。
- 修复前先记录失败现场（状态 JSON、日志、截图、命令输出）；修复后用同一观测面证明变化，不能用“看起来好了”。

### 7.3 失败即回退，不许叠加补丁

- 修完后任何原已 PASS 的用例变 FAIL：**立即停止叠加新改动**，先定位是本修复引入还是暴露旧缺陷；未定性前不得继续下一个功能。
- 不允许用“再补一个 if”掩盖回归；根因在共享状态/生命周期时，优先修正状态机与所有权，而不是加旁路。
- 一个修复若需要改动 3 个以上相邻模块，必须先更新设计文档与影响面矩阵，再分小提交逐个验证。

### 7.4 完成定义

一个修复只有同时满足以下四条才算完成：

- [ ] 原始故障有可复现的失败证据，且修复后有同一观测面的成功证据
- [ ] 影响面矩阵中“直接 / 相邻 / 全局”全部通过
- [ ] 原有相邻功能回归无 FAIL（不是“未测”，是实测通过）
- [ ] 失败路径被验证：端口占用、线程退出、手动断开、配置缺失等负向场景至少覆盖一项
