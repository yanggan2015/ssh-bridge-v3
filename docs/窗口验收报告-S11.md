- 日期：2026-11-22
- 构建：`output/build/ssh_bridge3.exe`（mingw-w64 静态链接，Win64；`--selftest` 退出码 0）
- 真机：本机 Windows，150% DPI，屏幕 1920×1080（工作区物理约 1920×1008）
- 桥接：`http://127.0.0.1:18086`；每个动作后回读 `/state`、`/ui-tree` 或实际端口/文件
- 测试通道：`loop1`、`ztl`(COM3)、`ok3568`(COM5)、`s6loop2`、`ssh-link-demo1`、`ssh-link-demo2`
- 服务面板：客户区 1120×632 DIP，注册 `svc.*` 控件 50 个（47 个业务控件 + 标题 + 2 个分组框）
- 最终二进制已实测退出：进程结束，18086/18082/69/111/1058/2049 全部无监听

## 一、结论

S11 **通过**。最终二进制上确认：

- 继电器两通道吸合/释放、脉冲 1/2、启用开关、反相开关、保存配置均有真实状态或回执；
- TFTP 在 UDP 69 可启动/停止，70 KB 上传 0.008 s、下载 0.007 s，MD5 一致；中文路径与越界拒绝通过；
- 共享 HTTP 在 18082 可启动/停止，`/`、`/browse`、多部分上传、下载、中文目录/文件名、删除均通过；端口冲突有明确中文提示；
- NFS 在 111/1058/2049 可启动/停止，`/share` 与 `/mnt/share` 两种别名都能 MNT 成功，逐级 LOOKUP 后 READ 255 B，MD5 与源文件一致；
- 面板“保存服务配置”与“保存继电器配置”连续操作不会互相覆盖；退出重启后端口、别名、根目录、允许写入均保持；
- 主窗口新增“断开”按钮后，COM5 可从 `ok3568` 通道释放，继电器随即可以复用 COM5；SSH 通道断开后“重连”也能真正重新上线；
- 串口应用层回显 **36 µs**；SSH 回显常态 **55–76 ms**，仅一次 122.6 ms 瞬时尖峰；一次 Enter 只回显一次；
- 面板 47 个业务控件两两重叠 **0**，最大 bottom 992，关闭按钮完整落在工作区内；主窗口工具栏新增按钮后无相互遮挡。

## 六、延时

| 路径 | 结果 |
| --- | --- |
| `loop1`（loop:ai） | 发送 14 B、接收 14 B，首包回显 **36 µs**，`echo_count=1` |
| `ssh-link-demo1` | 5 次常态 55.5/59.4/61.2/61.3/63.9 ms；一次 122.6 ms 瞬时尖峰；无 200 ms 以上 |
| `ssh-link-demo2` | 4 次 58.3/59.4/60.7/76.4 ms |
| 真实 Enter 路径 | 向 `term.view` 投递 `WM_KEYDOWN VK_RETURN` + `WM_CHAR '\r'`：`tx_delta=2`（一个 CRLF）、`echo_delta=1`，时延 72.1 ms，**无双回显** |
| `ztl`(COM3) | 打开 ready，发送 9 B、RX 0 B；硬件无回环，无法量应用层回显 |
| `ok3568`(COM5) | 打开 ready，发送 12 B、RX 0 B；硬件无回环，无法量应用层回显 |

SSH 常态时延与 ICMP RTT（约 54–86 ms）同量级，应用侧额外开销很小；没有出现之前 `ssh_channel_read_timeout(10ms)` 版本的 1.98 s 级退化。

## 七、启停、持久化与退出

- 启动：6 通道，在线 4（`loop1`、`s6loop2`、两个 SSH）；COM3/COM5 串口通道默认 idle。
- 断开/重连：
  - `ok3568` 打开 ready → 点“断开”后 state=idle，继电器 CH1 随即可用 COM5；
  - `ssh-link-demo1` 断开 idle → 重连 ready → 发命令回显 62.9 ms；
  - `ztl` 打开 ready → 断开 idle → 重连 ready。
- 配置持久化：面板保存后退出再启动，COM5、9600、69、允许写入、18082、`/share`、UID/GID 0 全部保持。
- 退出：通过 `menu.file.exit` 退出；进程消失；18086、18082、69、111、1058、2049 的 TCP/UDP 监听全部为 0。
- 测试拉起的 8 个 Chrome 进程已全部关闭。

## 八、本轮验收中修掉的问题

1. **服务配置互相覆盖**：`ServicePanel::save_config` 增加 `AppCore::set_service_config`，只同步 relays/tftp/share/nfs；实测 COM3 不被后一次保存改回 COM5。
2. **面板关闭按钮被任务栏压住**：客户区 700→640→632 DIP；最终 close 为 `1590,947,1740,992`，外框 bottom 1006。
3. **共享上传 multipart**：弃用 `mg_http_upload` 裸 PUT 语义，改 `mg_http_next_multipart`；Windows 中文路径用 `_wfopen`；上传/下载 MD5 一致。
4. **TFTP 端口冲突误报成功**：Windows 改 `SO_EXCLUSIVEADDRUSE`；冲突时返回中文可读错误。
5. **错误提示重复 `⚠`**：串口占用前置提示只保留一个。
6. **“请先停止该通道”却没有入口**：主窗口新增“断开”按钮与 `menu.view.disconnect`；COM5/SSH 都能断开并释放资源。
7. **停止后“重连”不生效**：`AppCore::reconnect` 对已停止通道调用 `start()`，SSH/串口均实测 idle→ready。

## 九、已知边界

- 继电器物理触点是否真正吸合无法从本机独立观测；本轮验证的是串口写入、状态机、回执与时序。
- COM3/COM5 当前没有硬件回环，发送有 TX、无 RX，因此不能给出串口端到端回显数值；应用层回显以 `loop:ai` 的 36 µs 为准。
- 共享 HTTP 默认无鉴权，适合本机/可信局域网；若要暴露公网需另加白名单或反向代理。
- NFS 用自写 ONC RPC 探针验证；没有安装第三方 NFS 客户端做系统级挂载。
- 服务参数在运行中修改不会热重启服务；需停止后重开才按新端口/别名生效。这是当前交互约定。
